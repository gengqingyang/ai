# CDN 故障采证

按以下顺序完成诊断，不要跳过证据直接给根因：

1. 从用户输入和内部意图路由元数据中确认故障类型、时间范围和现象。设备侧诊断需要设备 ID；装机截图已经包含可搜索的错误原文或错误码时，不要因为缺少设备 ID 阻塞源码诊断。
2. 先列出需要验证的 2 到 4 个假设，并为每个假设选择最小的只读证据集。
3. 按故障类型选择首要证据：
   - 装机、部署或初始化异常：先用 `search_code` 搜索截图错误原文或错误码，再用 `get_definition`、`find_references` 和 `read_file` 追踪触发条件。只有设备已经在线且源码证据不足时，才补充 `get_installation_evidence`。
   - 不跑量、流量偏低或突降：`get_traffic_evidence`
   - 插件安装、启动、版本或运行异常：`get_plugin_evidence`
   - 内核安装、切换或升级异常：`get_kernel_evidence`
   - IP、路由、DNS、网卡或配网异常：`get_network_evidence`
4. 代码工具只读取当前安全索引。所有源码事实必须引用 `path:line`；`snapshot.stale=true` 时要求执行 `/repo reindex`。源码版本与截图对应安装包版本不一致或无法确认时，只能给候选原因。
5. 设备结构化工具是只读快照。注意每份结果的 `data_source`、`collected_at` 和 `limitations`；其中网卡流量不等于 CDN 业务请求量，累计错误计数也不表示错误仍在持续发生。
6. 只有结构化工具明确缺少关键字段时，才使用 `run_tunnel_cmd` 补充最小的只读查询，并说明缺少什么证据。不要用任意命令重复采集结构化工具已经返回的内容。
7. 将截图事实、源码事实和设备事实分别按“已确认 / 已排除 / 仍待验证”整理。只有直接证据支持时才把某项写成已确认。
8. 需要处置时，先说明动作、原因、影响和风险，再调用受人工审批保护的工具。审批被拒绝后，根据拒绝理由调整方案，不要原样重试。
9. 最终回复先给结论，再列关键证据和下一步。工具数据标记为 mock 时必须明确说明，不得把 mock 当作真实节点事实。

遇到命令超时时，将执行结果视为未知；使用只读命令核实实际状态，不要立即重复同一个变更命令。
